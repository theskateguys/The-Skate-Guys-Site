## Reproduce

From the repository root, run the two Node commands above. For browser checks, start a static server on 127.0.0.1:4188 (for example, `python -m http.server 4188 --bind 127.0.0.1`), then:

```text
npx --package @playwright/cli playwright-cli -s=tsg-booking open http://127.0.0.1:4188/book.html
npx --package @playwright/cli playwright-cli -s=tsg-booking run-code --filename automation/check-booking-browser.js
npx --package @playwright/cli playwright-cli -s=tsg-booking close
```

Review screenshots are generated under `output/playwright/`; browser CLI artifacts under `.playwright-cli/`. These generated files are not part of the review commit. The browser fixture date is January 5, 2027; update it to a future date when reproducing later.

## Final timeout decision and commit preparation

On the user's subsequent request to finish and commit the review, the selected delivery deadline was **25000ms**, replacing 9000ms in `assets/lead-config.js` and the fallback in `assets/lead-capture.js`. Only the timeout value changes in lead-config.js; its production endpoint string, verified WhatsApp number and other settings remain unchanged. No push, merge, website deployment or Apps Script deployment is performed.

Rationale: the real browser acknowledgement took 9244.5ms; the measured Sheets phase took 12117ms before the rest of the response work; total instrumented doPost was 12394ms; an earlier full execution was 17983ms. Twenty-five seconds gives about seven seconds beyond that slow full execution for network/redirect/startup variation. Twenty seconds would leave only about two seconds. This is a chosen recovery deadline, not proof that every request will finish within it. Server performance should still be monitored and final optimized deployed code remeasured during the separately approved rollout.

`automation/check-booking-timeout.js` passed using the real browser's wall-clock timers and the actual repository config. It intercepts only the endpoint value for a synthetic server, not the configured deadline. It holds readable matching acknowledgements for 9245ms, 12394ms and 18000ms and checks that the UI remains pending until each response is read. A further held request reaches the 25-second client timeout: details remain, retry and WhatsApp stay usable, and the wording says "The browser timed out; storage may still complete." A late mocked server completion cannot create a saved state after client cancellation. A manual retry keeps the same ID/timestamp and message, receives duplicate_ignored and creates no additional mocked record. WhatsApp opening is intercepted and verified while delivery is still pending.

These timeout tests use **mocked network delivery**, not an additional real Google save or email. The actual browser/Google acknowledgement proof remains the earlier isolated version 1 result above. A preliminary controlled-clock boundary test also passed, including a response at 24999ms and timeout at 25001ms; the committed fixture instead uses actual wall-clock waits to make its execution/limitations straightforward to reproduce. The final new suite must not be presented as an additional deployed-server benchmark.
